# Missing-100-IV notification audit · 2026-09-25

## Fixed and tested

- **Repeated confirmation after DB failure:** Discord can accept a DM while the subsequent revision UPDATE fails. Keep its delivered/refused outcome in memory and retry only the DB acknowledgement. Discard obsolete outcomes when a new revision arrives.
- **Missed collection changes:** count + latest timestamp cannot distinguish two tiles swapped within one second. Include an order-independent 64-bit SHA-256-derived fingerprint of tile identities in the sync signature. This is probabilistic; hourly full reconciliation remains a backstop.
- **Recreated Poracle human with no rules:** invalidate the cached successful sync when the human disappears, even if cleanup finds no remaining rows.
- **Delayed opt-out publication:** reload Poracle immediately after cleanup, before confirmation DMs and rebuilds. Reload again after new committed changes when necessary; failures remain pending for retry.
- **Unclassified API timeouts:** wrap timeouts as PoracleError and log a useful reason even when the exception has no message.

Verification: 382 targeted tests passed, including 25 tests against a disposable MariaDB 10.11. Ruff and diff whitespace checks passed. Regression tests cover successful/refused delivery followed by acknowledgement failure, superseded revisions, recreated humans, reload ordering, collection swaps preserving count/time, and API timeout errors.

## Operational checks

- Spawn template keeps the 100% channel layout with the missing-Pokédex note. Settings messages use compact embeds.
- Discord image uploads are enabled. The reviewed preview has a Discord CDN map at 1104 × 500. If map generation/download fails, Poracle still attempts the textual alert; a map is not guaranteed during a tile outage.
- Read-only live query completed in approximately 9 ms. At audit time the player was switched off at confirmed revision 6 and collecting only shiny; zero managed rules and zero duplicate rules, as expected. No settings were changed by this audit.

## Remaining limitations and follow-up

1. **Delivery health in the site:** the confirmed state proves a settings DM was accepted, not that spawn alerts remain deliverable. Poracle can stop a destination after repeated delivery failures. Surface actual stopped/failed/sync status separately before wider rollout; preserve explicit player/admin stops rather than auto-restarting them.
2. **Crash window for confirmation duplicates:** the new outcome cache survives DB outages, not process restarts. A crash after Discord accepted a message but before the DB write may repeat it. Durable delivery records plus reconciliation would narrow this window; do not claim exactly-once delivery across Discord and MariaDB.
3. **Eventual consistency:** opt-outs and collection changes wait for the scheduler; settings saves wait at least 30 seconds before confirmation. Slow earlier scheduler steps, API outages and already queued Poracle jobs can extend the interval. Reloading promptly reduces this interval but cannot retract an already delivered alert.
4. **Monitoring:** track scheduler last-success age, reload failures, disabled Poracle destinations and map errors. Logs currently capture these failures, but there is no dedicated per-user notification-health status in the site.

This audit did not send preview DMs or modify player subscriptions.

## Follow-up completed

The first two follow-ups above are now addressed by migration 016/site 010:

- Durable pre-send journal plus nonce deduplication and post-restart history
  reconciliation replaces automatic retries of ambiguous sends. If Discord cannot
  prove delivery, the site offers an explicit new confirmation instead of guessing.
- Revision-scoped worker health distinguishes synced rules, stopped destinations,
  sync/API errors and stale checks. The site keeps polling while alerts are enabled.

Discord only enforces nonce uniqueness for a few minutes, which is why the durable
journal never automatically sends again for an existing claim:
https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx

Deployment checked: both local and public site returned HTTP 200, bot connected,
Poracle health OK, current settings remained off at confirmed revision 6. No new
confirmation attempts or messages were generated by the deployment checks.
The remaining eventual-consistency and external service availability limits still
apply. An explicitly requested retry may produce another confirmation if the user
already received the original; the UI asks them to check their DMs first.
