# Module detail (`modules/`)

Long-form version of the core module map: behaviour, limits and the reasons behind them. Quest and trade specifics live in `quests.md` and `trades.md`.

| Module | Responsibility |
|--------|---------------|
| `config.py` | Single `Config` class reading all env vars via `dotenv`. Source of truth for all settings. `load_dotenv()` fills only unset keys, and the test suite sets `PYTHON_DOTENV_DISABLED` after explicit pre-pinning (see `conventions.md`), so production-`.env` discovery stays disabled under `pytest`. `SHINY_ALERT_USER_IDS` defaults to `[MY_ID]`; only those pilot users ever get shiny DMs. |
| `database_connector.py` | `DatabaseConnector(database?)` — pymysql wrapper returning `list[dict]` from `cursor.description`. Default DB = `Config.DB_POLISWAG`; scanner DB passed explicitly. `unit(work, *args, read_timeout=5, dict_rows=True, autocommit=False)` runs a synchronous `work(connection, *args)` on a bounded connection of its own in a worker thread: committed when it returns, rolled back when it raises, always closed. It is the only way a module gets a connection; the module-level `connect(...)` beneath it is for this file and for host scripts. Conservative recovery, no SQL classification: bounded reconnect-and-retry is allowed **only before `cursor.execute` begins** (a `ping(reconnect=True)` or cursor-creation failure means nothing reached the server; retryable errnos are `2006`/`2013` plus `2003` from a failed internal reconnect, bounded by `retries`). Once execution starts there is **no replay** for either API, even reads — an arbitrary `CALL`/`WITH` can write and a `2006`/`2013` after execute or during commit leaves the outcome uncertain. The failure rolls back best-effort (never masking the caller) and raises the original error; only a failed rollback or a lost-connection (`2006`/`2013`) error refreshes/invalidates the handle for the next caller (a syntax-error rollback succeeds without refresh). `execute_transaction` never replays an uncertain commit; the next scheduler tick reconciles from stored state. Serialization: every call runs in a worker thread via `_run_serialized`, which holds the `asyncio.Lock` until the thread actually finishes — `asyncio.shield` keeps a cancelled waiter from releasing early, the next caller blocks until the outstanding thread is done, and cancellation still propagates to the waiter. |
| `http_client.py` | `fetch_data(endpoint_key, …)` — single shared `aiohttp.ClientSession`, reads from `Config.ENDPOINTS[key]`. In DEV (`not IS_PRODUCTION`) returns mock JSON from `mock_data/` for infra endpoints. |
| `scanner_status.py` | `ScannerStatus` — polls Dragonite (`/status`) + Rotom (`/api/status`) + Golbat DB. Renames a single `STATUS:` Discord voice channel with a combined down/expected-worker indicator in three states only (🟢 at least one worker up however thin the pool; 🔴 every worker down but the device connected; ❌ device offline or no data — no partial tier, it was pure rename-rate-limit churn) (expected counts read live from Dragonite per area, not hardcoded), fires HA webhook when scanner is fully down (15 min cooldown). Renames are budgeted locally (2 attempts / 10 min, 15 s timeout) because discord.py sleeps out a rename 429 (~600 s) inside `channel.edit()`, which used to stall the whole scheduler tick. Missing/unreachable data renders as ❌ but is excluded from the recovery-ladder trigger. Quest-scan progress counts, per registry area and on every check, both the stops with a valid quest and all stops inside the fence (`_count_area`, one query), so the total is always live: no stored per-area ceiling or recount script (migration `041` dropped the old `quest_expected_*` columns). Completion = flat count for 10 checks at ≥90% of the live total; never-stuck guards: 30 min flat below the floor accepts the ceiling, an empty fence counts as done, and an area at 0 quests for 2 h while others have quests stops blocking (all gated by scanner-alive). |
| `stack_recovery.py` / `device_manager.py` | Recovery aimed at what broke. Each pass `_diagnose(all_red, workers)`: rotom-ng workers 0 → `device_manager.phone_health()` over adb (the PoliSnatch loader's and the game's pids, and the installed game version against the one the phone last scanned with) → `phone` (loader or game not running) / `game_updated` (a Play Store update the release does not support: mods and owner told at once, nothing restarted) / `link` (healthy: the loader reconnects itself) / `unreachable`; workers but every Dragonite worker down → `no_data`; Dragonite or rotom-ng not answering → `stack`. Rungs at 5 and 15 min into the episode: phone = apps then full; stack = full, full; link = wait, full; no_data/unreachable = one mod notice, never a restart. "apps" brings the game, or the loader when the game is gone, to the front (never a force-stop: a Connect parks every account); "full" recreates dragonite+rotom-ng, waits 15 s, then the same. A reset is deferred while accounts or workers are still in use. Mod posts say down/why/how long/next; a green "back" follows any post. The episode survives a restart (`state/stack-recovery.json`). `ensure_wifi()` runs every pass: "Wifi is connected" + a gateway ping from the phone; after 3 dead checks in a row it toggles the radio and posts one mod notice per episode, never a reboot. `alert_if_offline()` alerts the mods after 15 min offline, then hourly, then every 6 h. The two switches (`auto_recreate_enabled`, `auto_reboot_enabled`) are columns read through `CachedBoolSetting`, at most every five minutes; there is no command for them since 2026-11-11. |
| `mention_rules.py` | `directed_mention(content, bot_id)` (a visible, unescaped tag; not one in code or a quote) and `replied_bot_message(message, bot_id)` (a reply to one of Poliswag's plain-text answers). Shared by `main.py`, which routes a message to the Mentions cog before any command, and by that cog. |
| `state_store.py` | `StateFile(name)`: a dict in `state/<name>.json` (atomic write, unchanged state not rewritten, a failed write only logged) and `still_running(state)` for episodes (seen in the last `EPISODE_MAX_AGE`, 30 min). Used by `stack_recovery.py` (`stack-recovery.json`: down since, rungs spent, what was announced), `device_manager.py` (`device.json`: offline since, last alert, Wi-Fi heal announced), `scanner_status.py` (`map-alert.json`: the open "Mapa sem dados" alert) and `account_guard.py` (`account-guard.json`: each rule's last alert and the pool level alerted). A restart in the middle of an outage therefore neither restarts the 5/15 min ladder nor repeats an alert, and the recovery notice still arrives. |
| `scheduler.py` | `StepRunner` and `Step`: runs the steps of the four loops in `cogs/scheduled.py`. Per step an interval (`every`) and a wait budget; a run past its budget is logged as ERROR and left in the background, never cancelled, and the step is not started again until that run ends. Records runs, failures, overruns, last and longest duration for `!ticks`. `progress_at()` is the heartbeat's time: the oldest of each loop's last finished pass and the start of any run past its budget. |
| `cached_bool_setting.py` | `CachedBoolSetting(poliswag, column, default=True)`: one boolean column of the `poliswag` table, read at most every `MAX_AGE_SECONDS` (300), so a change made in SQL takes effect within five minutes. A failed read returns the last value read, or the default when there is none yet, and is tried again on the next call. The column name goes into the SQL as text, so pass only a fixed name. Backs `auto_recreate_enabled` and `auto_reboot_enabled`. |
| `account_guard.py` | Account guard (2026-11-09), **alert-only**, production scanning stack only (the levelling stack is left out by the owner's choice): each tick reads the new lines of `dragonite` and `lork` through the Docker socket (since the last read; the first tick warms up with 15 min and only alerts on newer events) and keeps 15 min of two event kinds: `problem` (Dragonite `ACCOUNT PROBLEM`, with its worker) and `authfail` (Dragonite `Error during authentication`, lork `Authentication failed`). Rules: **worker** = one worker flags 3 accounts in 5 min (fake bans: 2026-11-05 20:36 Leiria_26 flagged one account every ~2.5 s as shadow banned); **fleet** = 5 flags from 3 workers in 10 min; **auth** = 20 failed logins in 15 min (normal days peak at 7; 2026-11-04 hit 96). Replayed over 2026-11-02..09 these fire only on the 11-04 and 11-05 incidents. A trip DMs the owner (`notify_owner`, tag `account_guard`) what it *would* pause: the worker's area (`enabled: false`) or every area. One DM per rule/key per hour. `MODE` is the switch for pausing later; production only. Also a **pool** check (2026-11-09): each tick reads Dragonite `ready` accounts (good + never used, via `account_monitor.get_account_stats`) and DMs when ready < 30 (low) and < 10 (critical); each level repeats at most hourly and re-arms silently at 40; no stats (Dragonite down) never alerts. Added after game RPC timeouts parked ~85 accounts per burst until midnight. |
| `scanner_manager.py` | Docker control (via `docker-py`) + `poliswag` table state (`last_scanned_date`, `scanned` flag). `is_day_change()` triggers a new scan cycle. |
| `quest_search.py` | `QuestSearch` — owns the scanner DB connection and the name maps. Quest lookup on the `pokestop` table, normalizing both scanner quest field sets. Strict liveness: production SELECTs carry `quest_expiry > UNIX_TIMESTAMP()` / `alternative_quest_expiry > UNIX_TIMESTAMP()`, and in-memory `_row_is_live` additionally drops any row whose carried expiry is missing, null, malformed or past — a row without a trusted future expiry is never live. Cached reads are gated by `_cache_usable` (1 h age **and** the stamp falls on today's Europe/Lisbon publication day). See `quests.md`. |
| `scan_areas.py` | The single source of scanned areas: reads the active `scan_area` rows (10 min cache) and their Dragonite geofences from `GET {DRAGONITE_API_URL}/v2/areas/` + `/v2/areas/{id}`, normalizing GeoJSON Polygon/MultiPolygon (holes respected) and Poracle `path`/`multipath`, and classifying points with ray casting. The last good fences are written atomically under `SCAN_AREA_CACHE` (`data/scan_areas.json`) and reloaded when Dragonite fails, so a scanner restart never empties the map. A point outside every active fence belongs to no area: `area_for` never guesses. Also provides labels, alert roles, Poracle names and the `sort_order` bit codes (`1, 2, 4, 8, 16`). Adding an area is a registry row plus its Dragonite area, never a code change. |
| `quest_exporter.py` | Writes `quests.json` / `quests-meta.json` for the PWA, skipping unchanged content. Candy (4), Mega Energy (12) and XL Candy (13) are species-specific with the website-compatible type kept exact (`candy`, `mega_energy`, `xl_candy`) and the species in the additive `pokemonId` field plus the grouping/id key (`type|#species|amount`); invalid species ids fall back to a species-less label. Each file is replaced atomically (same-directory temp file + `os.replace`, payload before metadata); the pair is not atomic — a crash between the two leaves a fresh payload with a stale meta, which the next export recovers by rewriting. A matching meta hash skips the write only when the on-disk payload is also usable (same content hash **and** `generatedAt` on today's Lisbon consumer day). See `quests.md`. |

**Scanner phone recovery (2026-11-09).** The phone is PoliSnatch's (Aegis retired 2026-10-31). `DeviceManager.phone_health` reads the loader and game PIDs and the installed Pokémon GO build in one adb call: `game_updated` when the build differs from the one the phone last scanned with (`remember_working_version`, hourly while scanning, `SCANNER_GAME_VERSION_FILE`), `broken` when the loader or the game is not running. The phone rung brings the game (or, without a game, the loader) to the front with `monkey`; it never force-stops. `game_updated` gets no restart: `StackRecovery` tells the mod channel and DMs the owner once, with the cause (a Play Store update the release doesn't support). The account guard no longer blocks the phone rung when Rotom has no worker in use (87 accounts held by waiting controllers deferred it for five hours on 2026-11-09). A new forced Pokémon GO version also DMs the owner, since the phone keeps scanning until the Play Store updates it.

**Scanner notices in the mod channel (2026-11-09).** `modules/scanner_notice.py`: every scanner notice (DeviceManager and StackRecovery `_notify`) edits the channel's latest message when it is Poliswag's scanner card (footer `Estado do scanner`), else posts a new card and deletes the previous one (id in `SCANNER_CARD_FILE`); the card shows "Em baixo desde" from the first failure and closes with the downtime. Owner DMs are unchanged.
