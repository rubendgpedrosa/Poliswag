# Conventions (full)

The core `docs/context.md` keeps the short version; this is the complete list.

- All modules receive `poliswag` (the bot instance) and access services via `self.poliswag.<module>`. The bot (`main.py`) is the one place that builds services and database handles; a cog builds nothing the rest of the bot uses. **Database access has one way in.** The bot holds a handle per schema: `poliswag.db` (the bot's own), `poliswag.scanner_db` (Golbat, read-only), `poliswag.site_db` (the site's `pogoleiria` schema) and `poliswag.poracle_db`. A single statement goes through the handle's shared connection (`get_data_from_database`, `execute_query_to_database`, `execute_transaction`). Anything bigger (statements that commit together, a read with its own timeout, work that must not queue behind the shared connection) is a unit of work: `await poliswag.site_db.unit(work, *args, read_timeout=…, dict_rows=…, autocommit=…)`, where `work(connection, *args)` is a plain synchronous function; the handle opens a bounded connection for it, runs it in a worker thread, commits when it returns, rolls back when it raises and closes. No module calls `connect()` or builds a `DatabaseConnector` (`tests/test_database_access.py` fails if one does; host scripts under `scripts/` are outside the bot and may). A class or function with no bot reference is given the handle by its caller (`TradeStats(site_db)`, `scan_areas.use(db)`). Do not open a unit once a minute when a check in memory can tell the work is not due.
- Admin guard: a `cog_check` (`str(ctx.author.id) in self.poliswag.ADMIN_USERS_IDS`) for a whole cog, `mods_only()` for a single command; no repeat check in the body.
- Three audiences: members, mods (`ADMIN_USERS_IDS`), owner (`MY_ID`), via `modules/permissions.py` (`is_mod`/`is_owner`; `mods_only()`/`owner_only()` for single commands). `!help` (`modules/help_command.py`) sections by the same gates: `_OWNER_COGS`, any `cog_check` (mods), or those predicates in `command.checks`. A command gated only inside its body shows to members — add the decorator. `!help` deletes its command message (in `prepare_help_command`). DMs are closed by default (`modules/dm_policy.py` `may_run_in_dm`): only the Pokédex (`!pokedex`/`!resumo`) and Shiny (`!shiny`) cogs are DM-exempt with their own membership checks; mods/owner pass by id. Tags go through `Mentions` (`cogs/mentions.py`) before command dispatch: owner Hermes chat uses plain non-command text or a visible bot tag only in DMs; one persistent private conversation spans those DMs. Explicit Claude/Codex jobs and blocked-task answers still need the tag in an owner DM and remain read-only; other permitted `!` commands still run untagged through `process_commands` (see `main.py`) but none starts an agent; a tag inside code or a quote is not a tag (`directed_mention`, shared by `main.py` and `Mentions`); all tagged server members, including the owner, get public Pokémon GO/PoGoLeiria answers (question, public map sample, event calendar, yesterday's aggregates; no private capabilities, credentials or internals) with `MentionLimiter` cooldowns; a bare mention greets instead of showing help; conversational DMs from non-owners stay silent. Replies disable mentions and never log prompt text or exception details. See `agents.md` for the data boundary and safeguards.
- Embed color: `Config.EMBED_COLOR = 0x4169E1`. Automated notices (owner DMs, mod-channel alerts, host scripts) go out as embeds, never plain text; plain text is for replies inside a flow (e.g. `!stats` follow-ups).
- Notification copy uses European Portuguese (PT-PT): describe shutdown/reboot as "desligar ou reiniciar o servidor", use natural singular/plural forms, and keep technical identifiers only where needed to identify a service or command.
- Tests under `tests/` (pytest). Run via `make test` inside Docker or `make test-local` locally (`pip install -r requirements-dev.txt`). Deterministic isolation: `tests/conftest.py` pins every env key `modules/config.py` reads before any `Config` import — `dotenv_values` on the explicit repo-root `.env.test` path plus explicit `os.environ` test-safe scratch defaults regardless of the starting cwd, then `PYTHON_DOTENV_DISABLED`, so ambient values and production `.env` discovery can never leak in. The only ambient values honoured are the disposable-integration selectors (`EVENT_SQL_TEST_PORT`, `HUNDO_SQL_TEST_PORT`, `HUNDO_SQL_TEST_PASSWORD`, `SPAWN_HISTORY_SQL_TEST_HOST`, `SPAWN_HISTORY_SQL_TEST_PORT`). A plain unit run never opens a real DB connection (autouse `pymysql.connect` patch); `tests/test_conftest_guard.py` fails when `config.py` starts reading a key with no deterministic test value. Quality gates, pinned in `requirements-dev.txt` and run in CI without unbounded reinstalls: `black --check .`, `ruff check .`, `vulture . --min-confidence 70`.
- Disposable SQL suites (`tests/integration/`, never production): `make test-sql` starts a separate `mariadb:10.11` container for each suite, on a Docker-assigned loopback port, waits for the server, runs the suite and removes the container even on failure. It requires Docker and the local Python development dependencies. The same `scripts/test_disposable_sql.sh` runs each suite in CI (optionally pass `events`, `hundo`, or `spawn`); it requires tests to execute without skips. Each suite requires its own marker schema and refuses servers with production-like schemas. Spawn's host selector is limited to loopback. A plain `make check` skips SQL suites unless separately opted in, so also run `make test-sql` for full CI coverage. Tests copy mock responses to a private session directory and refresh timestamps there; `make mock-data` remains an explicit update to development fixtures.

- The bot is one asyncio event loop: a synchronous database, Docker, subprocess or HTTP call reached from a coroutine goes through `asyncio.to_thread` (or uses an async client such as `aiohttp` / `asyncio.create_subprocess_exec`), otherwise it freezes the Discord heartbeat and every command for as long as it waits. Database work is already off the loop: the handle's query methods and `unit()` both run in a worker thread, so never wrap them in `to_thread`. Small local JSON state files are fine on the loop.
- State that must survive a restart: a column of the single-row `poliswag` table when the site or SQL needs it (watermarks, switches), otherwise a JSON file in `state/` (`Config.STATE_DIR`, git-ignored, bind-mounted; it was `logs/` until 2026-11-11). New files go through `modules/state_store.py` `StateFile(name)`: `load()` never raises, `save()` is atomic, skips an unchanged state and only logs a failed write. An **episode** (map down, phone offline, an open alert) is written with `seen_at` every time it is observed and picked up by the next process only if `still_running()` (seen in the last 30 min); an empty dict means none. Keep episode state in a file, not the database: the recovery ladder must read it when the database is what broke. Host scripts keep their watermarks in `state/` too (`pokedex-*.json`, `monitoring-discord-relay.json`). Run folders stay under `logs/` (`agent-jobs`, `hermes-runs`, `claude-runs`), as does `heartbeat`.
- Logging: `utility.log_to_file(msg, level)` → `logs/actions.log` (INFO; `"WARNING"` is written as WARNING) + `logs/error.log` (`"ERROR"`/`"CRASH"` only, which feeds the daily digest); the `poliswag` logger does not propagate, so each line reaches the console once. A per-minute operation that heals itself (version check, account card) logs a WARNING per failure and one ERROR when ten in a row have failed (`FailureStreak`), so only real outages reach the digest.
- Migrations: `setup_hook` replays every `migrations/*.sql` on each start (`modules/migrations.py`), before cogs load. No tracking table, so every statement must be `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`; `test_every_migration_is_rerunnable` enforces it.
- Scheduler: four `tasks.loop`s in `cogs/scheduled.py`, one pass a minute each, started 0/15/30/45 s after ready. **health**: scan areas, workers (status channel, recovery ladder, phone offline and Wi-Fi), account guard. **alerts**: quest scan and export, lure presence, trade announcer and DMs, 100IV, shiny odds, availability and alerts. **display**: the account card. **chores**: event fetch and posts, Niantic version, PoliSnatch update, the weekly, error and trade digests, traffic silence, masterfile. A new step goes in the loop whose members it may wait behind; nothing slow or third-party goes in health. Steps are `Step(name, run, every=, budget=)` run by `modules/scheduler.py`: `every` skips passes (300 s for the Niantic version, the PoliSnatch poll and the masterfile, 900 s for traffic silence; a step that already paces itself, like the event fetch with its 15 min cache, gets none), `budget` is how long the loop waits for a run (60 s; workers 300, masterfile 180). A step past its budget is **never cancelled**: it is logged once as ERROR ("still running after …", which reaches the owner's daily error digest), left running in the background while its loop goes on, and not started again until it ends (a WARNING, "ended after …"). So a step may find the next step of its loop running beside it, and two runs of one step never overlap. `!ticks` (mods) lists every step's last duration, age, failures and overruns. Constants counted in ticks (`PLATEAU_TICKS`, `WIFI_DEAD_AFTER`) belong to steps that run every pass; give a step with `every` a time, not a count. The digest groups repeated entries (same message with digits ignored) into one bullet with its count and first/last time, at most ten kinds, then a count of the kinds left out. Each pass ends by writing `logs/heartbeat` for the host watchdog; its time is the oldest sign of life among the four loops and any step past its budget, so one stopped loop or one hung step still lets it go stale (`docs/context/host-ops.md`). Digest markers are post-send only: the weekly calendar and the daily error digest persist their dedup markers after Discord accepts (quiet weeks / missing recipients advance immediately so they do not retry every tick; transport failures leave the marker unset for the next 60 s tick). Discord acceptance and the marker write are never atomic — a crash between batches or between send and marker may duplicate on retry. See `events.md`.
- This repo is the Discord bridge, not the game side. Native hooks, injector payloads, game opcodes and the fields they return, instrumentation and the interception proxy belong to PoliSnatch. `scripts/check_private_tech.py` enforces it in pre-commit and in CI; a line may opt out with `# poliswag-guard: allow` and a reason. The host-side shiny notes live in `/root/docs-archive/Poliswag/private/`, never here.
